      Mechanism · 机制详解

      vLLM 怎么「看见」Ascend，patch 又怎么改写 vLLM

      两个关键机制决定了 vLLM-Ascend 的存在方式：entry points 让它被发现，MonkeyPatch 让它在不 fork 源码的前提下改写 vLLM 行为。

      vLLM 侧机制

      ① entry points · 插件发现

      vLLM 启动时按「插件组名」扫描所有已安装包，找到 ascend 后调用 register()，拿回 NPUPlatform 的类路径并实例化。

      1. setup.py 登记 entry_points={"vllm.platform_plugins":["ascend = vllm_ascend:register"]}
      2. load_plugins_by_group("vllm.platform_plugins") 扫描 site-packages
      3. 发现 ascend → 调用 vllm_ascend.register()
      4. 返回类路径 "vllm_ascend.platform.NPUPlatform"
      5. vLLM import 并实例化 —— 此刻 vLLM 有了 Ascend 平台
      Ascend 侧手段

      ② MonkeyPatch · 运行时改写

      import vllm_ascend 会顺带 import 它的 patch/__init__.py，里面一串 import patch_xxx 以「import 副作用」的形式，把 vLLM 内部属性重绑成 Ascend 实现。

      # 改写前（vLLM 原版）
      vllm.config.CacheConfig.cache_dtype
      = {"auto","fp8","fp8_e4m3",…} ← 不含 int8
      # patch_kv_cache_dtype.py 在 import 时执行：
      vllm.config.CacheConfig.cache_dtype
      = … + {"int8"} ← Ascend 补上了

      三个真实 patch 例子

      1
      放开 KV cache dtype 校验
      16:35:36

      vLLM 侧 CacheConfig.cache_dtype 的合法枚举里没有 int8，但 Ascend 的 MLA / indexer KV 就要 int8。patch 把校验集合补上，vLLM 侧配置即可接受 int8。

      16:35:36patch_indexer_kv_dtype.py:102Patched indexer_kv_dtype to accept 'int8'
      16:35:36patch_kv_cache_dtype.py:115Patched cache_dtype to accept 'int8'
      2
      对齐 Attention Block Size 到 4480
      16:35:39

      hybrid 模型（GLM-5Next）同时有 MLA、recurrent-state、compressed-indexer 三种缓存。patch 把它们的 page size 对齐到 4480 tokens，避免一种缓存对齐失败导致整块浪费。

      16:35:39patch_mamba_config.py:121Setting attention block size to 4480
      16:35:39patch_mamba_config.py:158Padding mamba page size by 0.00%
      3
      替换 Worker 进程入口
      Worker import 时

      vLLM 默认起 Worker 子进程跑模型；vllm-ascend 把这个入口换成 NPUWorker。日志里 (Worker_DPx_EPx pid=…) 的前缀就是它起的进程名 —— 同一行看不到 patch 日志，因为它执行得比日志配置还早。

      16:38:48Worker pid=391612parallel_state.py:2267rank 2 … assigned as DP rank 2, EP rank 2 ← 已是 NPUWorker

      Process Topology · 进程拓扑

      26 个进程：为什么日志会重复 8 次

      一次 vllm serve 实际是 1 主进程 + 8 API server + 1 DP 协调器 + 8 EngineCore + 8 Worker = 26 个进程。per-rank 的代码在 8 个进程各跑一遍（×8）；patch / 配置校验在每个进程 import 时各跑一次（×24）。点任意节点看它的日志前缀与样本。
